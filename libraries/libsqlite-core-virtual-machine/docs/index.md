# sqlite-core-virtual-machine

`sqlite::core::virtual_machine` -- the VDBE bytecode interpreter: the
register machine every prepared SQL statement ultimately runs as. Phase 3 of
the [phased delivery plan](../../../SRS.md#12-phased-delivery-plan) in
[SRS.md](../../../SRS.md), and, per that plan, "the runtime half only... so
it can be validated by feeding it bytecode still generated by the legacy C
code generator during this phase." That validation strategy turned out not
to be achievable *in* this phase -- see below -- so this phase's scope was
renegotiated accordingly before implementation started.

## Position in the dependency graph

```
sqlite-utils
     |
sqlite-backend-os
     |
sqlite-core-virtual-machine      <- you are here
     |
sqlite-compiler                  (not yet built)
```

Depends on `sqlite::utils` (build plumbing only, via `sqlite_cpp_require_utils()`
-- no `sqlite::utils` header is actually included by this phase's opcode
subset). Does **not** yet link `sqlite::backend::os`: SRS S3.1 draws that
dependency edge for when this library gains database-file-touching opcodes
(`OP_OpenRead` and friends), which this phase's scope doesn't include (see
below) -- wiring the CMake link now, with nothing to exercise it, would just
be an untested edge.

## Why "validated by legacy-generated bytecode" was renegotiated

The SRS's own phase-3 description assumes the new VM can be handed bytecode
produced by the *existing* C `select.c`/`insert.c`/`where.c` code generator,
so its correctness can be checked against real `.test` suite behavior before
`sqlite-compiler` exists. That's not achievable standalone: the legacy code
generator emits `Vdbe`/`Mem` structures and expects a live `sqlite3`
connection, schema objects (`Table`, `Index`, `Column`), and a B-tree/pager
backing store -- none of which this refactor has built yet (schema handling
belongs to `sqlite-core-command-processor`, not started; real page storage
to `sqlite-backend-tree`/`-pager`, not started). Wiring actual interop would
mean building most of the rest of the engine first, defeating the point of
doing the VM as its own phase.

The scope this phase actually implements instead: a **real, complete
interpreter** for a **deliberately narrow opcode set** (arithmetic,
comparisons, control flow, row output -- see `opcode.hpp`), validated by
**hand-assembled programs** built directly with `aux::program_builder`, the
same builder API `sqlite-compiler-code-generator` will eventually drive.
Legacy-bytecode interop becomes a natural phase 4-5 task once that generator
exists and can target this same `program`/`instruction` representation.

## The `mem` value type: one representation, not several

`sqlite3_value` caches *multiple simultaneous representations* of one value
(both an integer and a string form can be valid at once) as a performance
optimization, with ownership tracked through a four-way
`MEM_Static`/`MEM_Dyn`/`MEM_Ephem`/`MEM_Term` flag scheme and a manual
destructor pointer. `aux::mem` instead holds exactly one canonical
representation, in a `std::variant`, and lets `std::string`/`std::vector`
own their own storage. This changes an internal performance/ownership
detail, not the observable type/value contract -- NULL/INTEGER/REAL/TEXT/BLOB,
type-affinity coercion (`as_integer()`/`as_real()`/`as_text()`), and
SQLite's NULL < NUMERIC < TEXT < BLOB ordering (`compare()`) -- which is what
FR-7 API compatibility ultimately depends on and what `aux/testing/mem_test.hpp`
checks.

## A real bug this library's own tests caught

`interpreter` originally stored `const program&` -- a non-owning reference,
mirroring how a first instinct might read "the interpreter runs a program
it's given." The very first test written directly as
`interpreter vm(builder.finish())` segfaulted: `finish()` returns a
`program` by value, that temporary is destroyed at the end of the full
expression, and `run()` then dereferenced a dangling pointer. `interpreter`
now owns its `program` by value (constructed by move), which is both safer
*and* a closer match to how legacy's `Vdbe` object actually works -- it owns
its `aOp` array outright, rather than borrowing one from somewhere else.
Concrete evidence, not a hypothetical, for why this refactor's own stated
acceptance bar (FR-10/FR-13: the C++ unit tests are additive verification,
not a formality) matters even for a phase with no legacy interop to check
against.

## What's out of scope this phase, and why

- **Most of the ~185 legacy opcodes.** `opcode.hpp` implements the subset
  needed to write and run genuine arithmetic/branching/row-emitting
  programs. The rest (`OP_OpenRead`, `OP_Column`, `OP_Rewind` and friends)
  drive B-tree cursors that don't exist yet; trigger/subquery/window-function
  opcodes need schema and the command processor; `OP_VFilter`/`OP_VUpdate`
  need the virtual-table layer. None are meaningful to stub without their
  real dependencies behind them.
- **`vdbesort.c` (external merge sort)** and **`vdbeblob.c` (incremental
  blob I/O)** -- both substantial standalone subsystems that need the
  pager/B-tree layer to be real.
- **`vdbetrace.c`** (SQL-text expansion for `EXPLAIN`/tracing) and
  **`vdbevtab.c`** (virtual-table cursor helpers) -- need schema/vtab
  infrastructure not yet built.
- **A distinct bound-parameter array.** `api::statement::bind_*()` writes
  directly into the shared register file rather than a separate `Vdbe.aVar`-
  equivalent, so (unlike real `sqlite3_reset()`) `reset()` here clears bound
  values too. See `api/statement.hpp`'s header comment.
- **Legacy's exact p1/p2/p3 operand convention** for the opcodes this phase
  does implement. Arithmetic here is `p3 = p1 <op> p2` (left, right, dest);
  comparisons are `if r[p1] <op> r[p2] then goto p3`. Both are chosen for
  readability in this phase's hand-authored test programs and do not match
  `vdbe.c`'s own (more historically-accreted) register assignment for the
  same opcodes -- there is no legacy-code-generator caller to match yet, so
  there is nothing this convention needs to be compatible with today.

## Building and running tests independently

```sh
cmake -S libraries/libsqlite-core-virtual-machine -B build-vm
cmake --build build-vm
ctest --test-dir build-vm
```

Or, as part of the workspace build: `ctest --test-dir build -R sqlite-core-virtual-machine`.

## Consuming this library

```cmake
include(cmake/SqliteCppDependency.cmake)
sqlite_cpp_require_core_virtual_machine()
target_link_libraries(your_target PRIVATE sqlite::core::virtual_machine)
```
